# VulcanBench Verdict v2 design

Suite id `verdict-v2`. Status: design, 2026-09-24. Rules are logged in
[DECISIONS.md](DECISIONS.md) (2026-09-24 entry); this file is the working
spec for building the item set.

## Why v1 is being replaced

Verdict v1 asked a System One model (a model that returns a typed decision,
not text) to judge Frontier v4 patches. Three problems made its headline
uninformative:

1. **One skill.** Four of its five families asked different questions about
   the same 745 patches, so their errors correlated and the suite measured
   one thing: patch review on binary-parity tasks.
2. **An unbalanced headline.** 63% of patches pass, so "always answer
   passes" scored 62.7% and Jev scored 62.8%. Accuracy on a skewed yes/no
   question cannot separate a model from the floor.
3. **A shortcut.** Lines changed alone ranked the pass question better than
   Jev (AUROC 0.785 against 0.690), because pass rate climbs with patch size.

v2 fixes each one: many independent skills, balanced items with the floor
stated, and shortcut baselines that every family must defeat before it ships.

## What a v2 item is

Same shape as v1 (`harness/verdict/items.py`): a `state` (what the model
reads, at most about 32k tokens), one typed `question` and a verified
`answer`. Question types are the three the System One API offers:

- `noul`: probability that a statement is true (yes/no)
- `choice`: one of up to 255 options
- `score`: an ordered level

The answer always comes from executing code or a deterministic tool, or
exists by construction in a generator. Never from a model's opinion.

## Families

Twenty families in eight areas, two pillars. "Pair" means two candidates
with exactly one correct, position randomised, so the floor is exactly 50%.

### Software pillar

| Area | Family id | Type | Question | Ground truth | Source |
|---|---|---|---|---|---|
| Reading code | `code-output` | choice (4) | What does this short program print? | Execute it; distractors are outputs of mutated versions | Generated |
| Reading code | `type-check-pair` | choice (pair) | Which snippet passes the type checker? | mypy, tsc or cargo check | Generated from real-library snippets plus single-edit mutations |
| Reviewing changes | `patch-pair` | choice (pair) | Two patches for one issue: which passes the hidden tests? | Frontier v4 verifier | Run archive, pairs matched on lines changed |
| Reviewing changes | `failing-test` | choice (list) | Given a patch, which of the listed hidden tests fails? Exactly one listed test fails; the rest passed | Per-test verifier results | Run archive |
| Finding bugs | `fix-file` | choice (list) | Which file does the fix touch? | The merged fix | Multi-file OSS tasks (v4-new, VulcanCyber, Routine) plus mined post-cutoff PRs |
| Finding bugs | `bug-function` | choice (list) | Given a failing test's output, which function holds the planted bug? | The planted mutation, confirmed killed by the test | Generated over real OSS modules |
| Security | `vuln-pair` | choice (pair) | Before and after a security fix: which version is vulnerable? | The fix commit | VulcanCyber pool plus mined 2026 advisories |
| Security | `weakness-class` | choice (about 10) | Which weakness class is this? | Advisory CWE, collapsed to about 10 families | Mined 2026 advisories |
| Testing | `mutant-kill` | noul | Does this test catch this change? | Run the test against the mutant | Generated over real OSS modules |
| Testing | `expected-value` | noul | Is this assertion's expected value correct for the spec? | Reference implementation | Generated |
| Operations | `incident-root-cause` | choice (list) | Logs from several services during an incident: which service caused it? | The simulation that generated the logs | Generated |
| Operations | `semver-impact` | score (3) | Patch, minor or major version bump? | cargo-semver-checks, griffe, api-extractor | Mined library releases |

### General pillar

All general families are generated by code with fresh seeds per build, so
no item exists anywhere online and none can be memorised.

| Area | Family id | Type | Question | Ground truth |
|---|---|---|---|---|
| Logic | `constraint-pick` | choice (4) | Which assignment satisfies every rule? | Constraint solver; exactly one option satisfies |
| Logic | `entailment` | noul | Does the conclusion follow from the premises? | SAT solver; nonsense predicate names block world knowledge |
| Math | `word-problem` | choice (4) | Multi-step problem with random numbers | Computed; distractors are common slips (wrong operation order, dropped step, unit error) |
| Math | `estimate-band` | score (5) | Which band contains this computed quantity? | Computed |
| Tables | `table-lookup` | choice (list) | Which row or group answers this question about a table? | pandas over a generated 30 to 200 row table |
| Tables | `table-count-band` | score (5) | How many rows match this filter? | pandas |
| Rules and policy | `policy-decision` | noul | Under this policy, is this case allowed? | Rule engine that generated the policy |
| Rules and policy | `policy-clause` | choice (list) | Which clause decides this case? | Rule engine |

## Scoring

### Per family

- **Skill (the headline unit).** `100 * (acc - floor) / (1 - floor)`, where
  `acc` is accuracy of the model's own top answer and `floor` is the best of
  the trivial baselines for that family: majority answer, uniform guess, and
  every shortcut baseline listed below. 0 means no better than the best dumb
  strategy, 100 means perfect. Negative values are published, not clipped.
- **Ranking.** AUROC (macro one-vs-rest for choice), threshold-free.
- **Calibration.** Brier skill score against the base-rate forecast, and ECE.

For `noul` families built at a 50% base rate the top answer and the 0.5
cutoff coincide, so no fitted cutoff is needed. For `score` families,
accuracy is exact-level and the report adds mean absolute level error.

### Headline

- **Verdict Index**: mean family skill over all shipped families.
- **Software** and **General** sub-indices: the same mean within each pillar.
- **Calibration Index**: mean Brier skill score, shown beside the Verdict
  Index, never folded into it.

Every index carries a 95% bootstrap interval, resampling source units (task,
repo, or generator seed group), not items, so correlated items do not
narrow it falsely. Two models whose intervals overlap are reported as not
separated, never ranked.

### Shortcut baselines

Each family ships at least one cheap baseline that uses surface features
only. The ones known in advance:

| Family | Shortcut baselines |
|---|---|
| `patch-pair` | Larger patch, smaller patch, patch touching more files |
| `failing-test` | Test name with most token overlap with the patch; first/last listed |
| `fix-file` | File with most token overlap with the issue; largest file |
| `vuln-pair` | Longer version; version with more input checks by keyword count |
| `code-output`, `word-problem` | Most frequent option shape; option nearest the mean |
| `failing-test` | Leave-one-out task prior (the test this task's other patches fail most) |
| `incident-root-cause` | First service to log an error, most errors, most depended on |
| `table-lookup` | First row; row with largest value in the named column |
| All `noul` | Statement length; majority |
| All `score` | Middle level; majority level |

Builders balance items so these land near chance; the admission gate checks it.

## Admission gate (per family, applied in the pilot)

A family ships only if all hold on its pilot items:

1. The reference model (GPT-6 Astra, high effort, through Codex on the
   subscription, same state, no tools) scores skill between 40 and 95:
   answerable, and not saturated.
2. The best shortcut baseline scores skill of 15 or less.
3. At least 200 test items from at least 20 independent source units,
   split into dev and test by source unit.
4. Ground truth re-verified on a 5% random sample by re-execution.

A family that fails is rebuilt once (harder distractors, better balancing)
or cut. Cuts are listed in the report. The pilot is 30 items per family.

## Changes during the build

- `ci-failure` (2026-09-24) was replaced by `incident-root-cause`. The run
  archive records only per-test pass or fail, not test output, so there was
  nothing to label; re-running stored patches would compete with the live
  serial sweeps, and a 12-patch trial reproduced only AssertionError, so the
  label would have been nearly one class.
- `failing-test` (2026-09-24) shows one failing target plus the targets that
  passed, whatever the number of failing targets. Capping patches at two
  failing targets left 70 items once the task-prior shortcut (61 to 72%
  uncapped) was held to 25%.

## Rows on the chart

- **Jev** (pinned version, one column: the API has no effort setting).
- **GPT-6 Astra (reference)**, labelled as a reference row that shows the
  questions are answerable. It is not a leaderboard entry and no other LLM
  rows are added in v2.
- **Best shortcut** and **floor**, per family.

## Integrity

- Item files are private, gitignored (`verdict-v2-items/`) and canaried,
  like v1. Software items embed benchmark tasks.
- Generated families use a fixed build seed recorded in the item file; a
  re-run of the suite uses the same seed, a new version uses a new one.
- Mined sources (OSS PRs, advisories) must post-date 2026-06-01.
- Dev split is used only for fitting and prompt wording; results are test
  split only.

## Scale and cost

About 200 test and 50 dev items per family, 20 families: about 5,000 items.
Jev at $0.042 per million input tokens costs roughly $1 to $2 for the full
set. The reference model runs through Codex on the ChatGPT subscription,
which keeps it clear of the Claude subscription used by the serial Frontier
v4 chains.

## Build order

1. Framework: family registry, skill and index scoring with bootstrap by
   source unit, shortcut baseline hooks, per-family builders writing one
   JSONL.
2. Archive families: `patch-pair`, `failing-test`.
3. General families (all generated): the eight general families.
4. Generated software families: `code-output`, `type-check-pair`,
   `mutant-kill`, `expected-value`, `bug-function`, `incident-root-cause`.
5. Mined families: `fix-file`, `vuln-pair`, `weakness-class`,
   `semver-impact`.
6. Pilot (30 items per family, Jev plus reference), gate, rebuild or cut.
7. Freeze, full run, report, card, site page.
